# Linkコンパイラ v0.1 — AST構文からRustバイナリへ

Pythonスクリプトの代わりに **`.link` ファイル（ASTそのもの＝S式）** を書き、
Rustソースを経由してネイティブバイナリを出力するコンパイラの試作。

```
.link (AST) ──linkc──▶ .rs (Rust) ──rustc -O──▶ ネイティブバイナリ
                                                    ※実行時にPython不要
```

正直な注記：コンパイラ本体 `linkc.py` は現状Python製（ブートストラップ段階）。
「Pythonに代わる」のは **プログラムを書く言語と実行系** であって、
生成されたバイナリはPythonに一切依存しない。
コンパイラ自体のRust移植（自己ホスト）が次の段階。

## 使い方

```sh
export PATH="$HOME/.cargo/bin:$PATH"     # rustc 1.99.1（この環境に導入済み）
python3 linkc.py examples/demo.link  -o out/demo  --run
python3 linkc.py examples/bench.link -o out/bench
./out/bench                              # バイナリ単体で実行できる
```

## 言語仕様 v0.1

プログラムは `(program 文...)`。文法＝抽象構文木そのもので、字句解析後の木を直接書く。

| 種類 | 構文 |
|---|---|
| 型 | Scalar=`f64`、Vec=`Vec<f64>`、Mat=`Vec<Vec<f64>>`、Bool。静的に推論・検査 |
| 変数 | `(let x 式)`、`(set x 式)`、`(set-idx v i 式)` |
| 制御 | `(for i n 文...)`、`(for i start end 文...)`、`(while 条件 文...)`、`(if 条件 文 文)`、式としての `(if 条件 式 式)` |
| 算術 | `+ - * /`（スカラー同士、ベクトルの要素積、スカラーとのブロードキャスト、行列は加算とスカラー倍）、`sqrt exp log abs sin cos`、`neg` |
| ベクトル | `(vec ...)`、`(zeros n)`、`(ones n)`、`(iota n)`、`(len v)`、`(idx v i)` |
| 出力 | `(print ラベルや式...)`（型に応じて整形） |

### Link核演算（既存の数学用語で命名）

| Link構文 | 意味 |
|---|---|
| `(dot a b)` | 内積 Σ aᵢbᵢ（クロストーク内積） |
| `(outer a b)` | 外積 aᵢbⱼ（ランク1行列） |
| `(gram a b ...)` | Gram行列 Gᵢⱼ = ⟨vᵢ, vⱼ⟩ |
| `(matvec M v)` / `(matmul A B)` / `(transpose M)` | 行列ベクトル積・行列積・転置 |
| `(cumsum v)` | 累積和作用素 L |
| `(diff v)` | 離散微分 D。**D∘L = 恒等写像**（下記で誤差0を確認） |
| `(norm v)` | √(⟨v,v⟩) |

## 検証結果（2026-10-24、このVMで実測）

**demo.link**（全て期待値と一致）：
dot=20、norm(a)=√30=5.477225575051661、gram=[[30,20],[20,30]]、
matvec(outer(a,b), b)=30a=[30,60,90,120]、cumsum=[1,3,6,10]、
diff(cumsum(a))=a（往復誤差ちょうど **0**）。

**bench.link vs Python**（同じ計算：Σ√i を10⁷回ループ＋10⁶要素の累積和・差分往復）

| | 時間 | 出力 |
|---|---|---|
| Linkバイナリ | **0.074 s** | sum_sqrt = 21081852648.716972 |
| Python（ループは純Python、ベクトル部はNumPy） | 1.966 s | 同一の値 |

約27倍（この計算・この環境での実測値。一般的な主張ではない）。
出力は全項目で完全一致。コンパイル時間は約1秒で、これは一度きりのコスト。
累積和の往復誤差0は、値が2⁵³未満の整数で厳密に表せるため数学的にも当然の結果。

## 既知の制限（v0.1）

- SVD・固有値分解がない（PCA持ち上げ実験を書くには次段で追加が必要）
- 関数定義なし、文字列はprintラベルのみ、エラー処理なし
- `(idx v i)` はベクトル全体を複製する生成コードで、ループ内多用は非効率
- 行列演算は最小限（加算・スカラー倍・積・転置のみ）

## v0.2 直接バイナリ出力（linkbin.py）— Rustを経由しない

```
.link (AST) ──linkbin──▶ x86-64機械語バイト列 ──▶ ELF実行ファイル
                         ※rustc・リンカ不使用。バイト列そのものを生成・出力する
```

```sh
python3 linkbin.py examples/demo_bytes.link -o out/demo_bytes --run [--hex]
# バイト列は out/demo_bytes.hex にも保存される（hexダンプ形式）
```

- 整数方言のみ：64bit符号付き整数、`let/set/for/while/if`、`+ - * / mod`、比較、
  `(print "ラベル" 式...)`（10進出力ルーチンも機械語で自作、libc不使用・syscall直接）
- 検証（2026-10-24）：demo_bytes.link の全出力が期待値と一致
  （Σ1..100=5050、10!=3628800、fib(20)=6765、100/7=14、100 mod 7=2、負数・0・while・if）。
  ランダム生成した算術式50件でもPython評価と全件一致。
- サイズ比較：同じ「プログラムをネイティブ化する」でも、直接バイト列版は **1,747バイト**、
  Rust経由版は4.4MB（約1/2600）。sha256 でバイト列の同一性を確認できる。
- 制限：浮動小数点・ベクトル・Link核演算（内積等）は未対応で、それらはRust経由（linkc）が担当。
  2つのバックエンドの統合が次の課題。

## v0.3 入力をデータにする — 標準入力（read-int）

プログラム（作用素）は固定し、入力は実行時にデータとして流し込む。

```lisp
(let x (read-int))        ; 標準入力から次の整数を読む（空白区切り、負数可）
(read-eof?)               ; 入力が尽きたら 1（linkbin側）
```

- linkbin側：入力リーダ自体も機械語で自作。read(0) システムコールを
  4,096バイトバッファで回し、数字をその場で値に変換する。libc不使用は不変。
- linkc側（Rust経路）：`(read-int)` は次の空白区切りトークンを f64 として読む。
  入力が尽きたら 0.0 を返す。
- 使い方の型は2つ：
  - `examples/stats.link`：先頭で件数 n を読み、続く n 個を処理（合計・最大・最小・平均）
  - `examples/streamsum.link`：EOFまで読み続ける（件数・合計・二乗和）。読み切り型は
    「最初の1個を読んでから `(while (== (read-eof?) 0) ...)` で回す」形
- 検証（2026-10-24）：負数・末尾改行なし・空入力・n=0 を確認。
  ランダム列5試行（最大3,000個・16KB、バッファ境界を跨ぐ入力を含む）で
  Python集計と全件一致。同じバイナリがデータ次第で違う答えを出す
  ＝ バイナリ内にはデータも答えも入っていない。

## v0.4 1×1 Link中間表現（linkir.py）

ASTとコード生成の間に、共通IRとして **1×1 Linkグラフ** を挟む。

```
1つのノード = y = F(x ; s)
  x = 通過信号（ちょうど1本）／ s = クロストーク信号（最大1本、横から来る別の鎖の出力）
  F = 素演算1つ（aff / add / mul / fn / cmp / read ...）
```

式は「左端の背骨が通過経路、右の部分式は別の鎖から横供給」として分解される。
定数係数は `aff y = p·x + q` に畳まれ、**変数の係数はクロストークとして入る**。

最適化はアフィン鎖の合成縮約（区間縮約そのもの）：
`(p2,q2)∘(p1,q1) = (p2p1, p2q1+q2)` で閉じるので、アフィン区間は1本のLinkに潰れる。
原子（sqrt等）と動的係数（クロストーク）が来た所で合成は止まる
＝「アフィンの場合は閉じる」という既知の境界と一致する。

実測（2026-10-24）：`((((x*2)+3)*4)-5)` は `aff x*8+7` の **1本** に縮約。
affine.link 全体で 34 → 19 本。ランダム式300件（両評価器とも未定義の30件を除外）で
直接評価と全件一致。streamsum.link は linkbin バイナリと出力一致。
既存理論との対応：制御理論の信号フローグラフ、自動微分のWengert listと同型の部分が多い。
独自性があるとすれば「係数も信号（クロストーク）」と「縮約代数を最適化の中心に置く」設計。

既知の制限：IRの `if` は両分岐のノードを評価する（純粋な式でのみ等価。
read-int を分岐内に書くとずれる）。共有された部分式の重複排除（CSE）は未実施。

### 縮約は2種類ある：区間縮約と境界縮約（--mode）

- **区間縮約（interval）**：区間全体を合成して1本にする。内部を全部「圧縮」する。
- **境界縮約（boundary）**：区間は合成しない。隣り合う2本が継ぎ目でちょうど打ち消す
  （逆対）ときだけ消し、入力境界と出力境界を直接つなぐ。打ち消しの条件は継ぎ目の
  パラメータだけで判定する：アフィン対 `p2·p1 == 1 かつ p2·q1 + q2 == 0`（浮動小数点でも厳密に）、
  同じクロストークが出入りする add/sub 対・mul/div 対、exp/log 対、恒等Link。
  ＝「圧縮するのではなく、打ち消す」。

実測（2026-10-24）：

| | ノード数 affine.link | ノード数 adversarial | a=(1+1e16)−1e16 | b=1e200·1e200·1e−200 |
|---|---|---|---|---|
| none（書いたまま） | 34 | 17 | 0（消える） | inf（溢れる） |
| boundary | 22 | 5 | 1（復活） | 1e200（復活） |
| interval | 19 | 5 | 1 | 1e200 |

境界縮約は構成的な鎖（逆対のない鎖）では区間縮約ほど減らない（22 vs 19）。
代わりに、触るのは「ちょうど逆対」だけで、意味の変更が局所的。
どちらの縮約も実数では厳密だが浮動小数点では書いたままの評価とは一致しない
（むしろ厳密な値を「復活」させる方向にずれる）点に注意。

境界公式の検証：各点が原点からの蓄積Link（境界蓄積量）を持つとき、区間 a→b の
Link は境界だけから `L_b ∘ L_a^{-1}` で決まる。有理数（Fraction）でランダムな
アフィン鎖1,000件を検算し、逐次合成と **完全一致**（浮動小数点の影では相対偏差
最大 1.5e-11、丸めのみ）。内部に触れずに区間が決まる＝離散版の基本定理の形。

### 境界の定義（私案に合わせて再実装、boundary.py）

境界とは **切り替わり点**（例：−1から1へ切り替わる点）。ストリームは
「初期値 + [(位置, 跳び)]」だけで表され、内部は変化がないので情報を持たない。
抽出は離散微分そのもの、復元は累積和そのもの。

```sh
python3 boundary.py encode < stream.txt     # 数列 → 境界イベント
python3 boundary.py decode < events.txt     # 境界イベント → 数列
python3 boundary.py stats  < stream.txt     # dense/区間/境界のサイズ比較
python3 linkir.py prog.link --run --sparse-input --tokens "..."   # 入力を境界経由で流す
python3 linkir.py prog.link --run --trace s                       # 変数の軌跡を境界解析
```

実測（2026-10-24）：整数値ストリームのランダム200件で復元誤差ちょうど0
（浮動小数点ストリームでも今回の200件では0だが、一般には a+(b−a)=b は保証されない）。
入力2,000サンプル（切り替わり2回）は境界5個に潰れてから streamsum に流れ、結果は直接入力と一致。
実行トレース解析では、100,001サンプルの軌跡が境界4つ（+初期値=5個）で復元誤差0。
なおグラフ側の縮約（継ぎ目打ち消し、--mode boundary）は担当側の解釈として残置し、
私案の境界定義はこのストリーム表現が正本。
